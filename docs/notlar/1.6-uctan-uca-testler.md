# 1.6 Uçtan uca testler (Playwright)

Bu adımda uygulamayı **bir kullanıcının gözünden** test eden Playwright
testlerini ekledik. Gerçek bir tarayıcı açılıyor, gerçek sunucuya bağlanıyor,
formları dolduruyor, butonlara tıklıyor ve sonucu ekranda arıyor.

## Üç tür testimiz var

| Tür        | Komut              | Ne dener                                       | Hız            |
| ---------- | ------------------ | ---------------------------------------------- | -------------- |
| Birim      | `npm test`         | Tek bir fonksiyon (slug, imza, izinler)        | Milisaniyeler  |
| Veritabanı | `npm run test:db`  | İş kuralları + gerçek PostgreSQL               | Saniyeler      |
| Uçtan uca  | `npm run test:e2e` | Tarayıcı + sunucu + veritabanı, hepsi birlikte | Onlarca saniye |

Hepsini uçtan uca yazmıyoruz çünkü yavaşlar ve bir test düştüğünde hatanın
nerede olduğunu söylemezler. Ayrıntılı kuralları (örneğin "eski aboneliğin
iptali yeni aboneliği bozmasın") birim ve veritabanı testleri dener. Uçtan uca
testler ise parçaların **birbirine doğru bağlandığını** dener: form doğru
action'a gidiyor mu, çerez yazılıyor mu, yönlendirme doğru sayfaya mı gidiyor,
middleware isteği engelliyor mu.

## Testler

| Dosya                  | Senaryolar                                                                                                                                                                                      |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `e2e/auth.spec.ts`     | Kayıt → e-posta doğrulama → çıkış → yanlış şifre → giriş. Aynı e-postayla ikinci kayıt. Şifre sıfırlama (diğer cihazdaki oturum da kapanır). Girişten sonra başka siteye yönlendirme yapılamaz. |
| `e2e/teams.spec.ts`    | Davet edilen kişi kayıt olup ekibe katılır, rolüne göre sekmeleri görür. Tek sahip ayrılamaz. Yabancı biri ekibin sayfalarında 404 alır.                                                        |
| `e2e/billing.spec.ts`  | Ücretsiz plan 5 kişide durur, faturalandırma sayfası sayıyı doğru gösterir.                                                                                                                     |
| `e2e/security.spec.ts` | Girişsiz kullanıcı yönlendirilir. Başka siteden POST 403 alır. Webhook imzalı isteği kabul eder, sahteyi reddeder.                                                                              |

## Testler e-postaları nasıl okuyor?

Kayıt ve davet akışları e-postadaki linke tıklamayı gerektiriyor. Testler için
`sendEmail` artık `EMAIL_OUTBOX_FILE` verildiyse her e-postayı o dosyaya bir
satır JSON olarak da yazıyor. `e2e/helpers.ts` içindeki `linkFromEmail`, bir
adrese gelen son e-postadaki linki oradan buluyor. Kullanıcının gelen kutusunu
açmasının test versiyonu.

## Testler birbirini nasıl bozmuyor?

- **Ayrı veritabanı ve port.** Testler `saas_e2e` veritabanını ve 3100
  portunu kullanır. `npm run dev` (3000, `saas`) açıkken de çalıştırabilirsin,
  kendi verine dokunmaz.
- **Her test kendi kullanıcısını açar.** `uniqueEmail("ali")` her seferinde
  `ali-3f9a1c2e@ornek.com` gibi yeni bir adres üretir. Bu sayede testler
  paralel çalışabiliyor.
- **Başlamadan önce temizlik.** `e2e/global-setup.ts` veritabanını hazırlar,
  eski veriyi ve e-postaları siler.
- **Sabit ortam.** `e2e/env.ts`, senin `.env` dosyandaki gerçek GitHub ve
  Stripe anahtarlarını ezer. Testler Stripe'a hiç istek atmaz.

## Bir test gerçekten işe yarıyor mu?

Hep geçen bir test bir şey kanıtlamaz. Kontrol etmenin yolu, kodu bilerek
bozup testin düştüğünü görmek ("mutation testing"). Bu adımda iki şeyi
bozup denedik:

1. Ücretsiz plan sınırını 5'ten 6'ya çektik → `billing.spec.ts` düştü.
2. Middleware'deki CSRF engelini kaldırdık → `security.spec.ts` düştü.

Sonra ikisini geri aldık. Kendi testlerini yazarken de bunu yapmanı öneririm.

## Kendi bilgisayarında çalıştırmak (Windows)

1. PostgreSQL açık olsun (`npm run db:up`).
2. İlk seferde tarayıcıyı indir:

   ```bash
   npx playwright install chromium
   ```

3. Testleri çalıştır:

   ```bash
   npm run test:e2e
   ```

   Sunucuyu Playwright kendisi başlatır (`next dev`, port 3100). İlk
   çalıştırmada sayfalar derlendiği için yaklaşık bir dakika sürer.

Faydalı seçenekler:

```bash
npx playwright test --ui               # Görsel arayüz: testleri tek tek çalıştır, adım adım izle
npx playwright test --headed           # Tarayıcıyı görerek çalıştır
npx playwright test e2e/auth.spec.ts   # Sadece bir dosya
npx playwright show-report             # Son çalıştırmanın HTML raporu
```

`--ui` modunu mutlaka bir kez dene: her adımda sayfanın ekran görüntüsünü,
ağ isteklerini ve konsolu görebiliyorsun. Hata ayıklamanın en kolay yolu.

## CI

`.github/workflows/ci.yml` içine `e2e` adında ikinci bir iş ekledik.
Mevcut kontrollerle paralel çalışır: PostgreSQL'i başlatır, Chromium'u kurar,
uygulamayı derler (`npm run build`) ve testleri `next start` ile çalıştırır.
CI'da bir test düşerse bir kez daha denenir; ikincide de düşerse gerçek
hatadır.

Test düştüğünde Actions sayfasında, o çalıştırmanın altındaki **Artifacts**
bölümünden `playwright-report` dosyasını indirebilirsin. İçinde düşen testin
ekran görüntüsü ve `trace.zip` var. `npx playwright show-trace trace.zip` ile
testin her adımını yeniden izleyebilirsin.
